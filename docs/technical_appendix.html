8.1 Configuring the dashboard

The dashboard’s study-specific settings are held in one file: dashboard.yml. This keeps choices such as study dates, site targets, reminder thresholds, cycle-inference rules, and display limits separate from the R analysis code.

What this means. Most routine adaptations should require a change to the configuration file followed by a fresh render—not edits scattered through the analysis pages.

Why it helps. Keeping assumptions in one clearly annotated file makes them easier to review with the study team, apply consistently across all pages, and record when the dashboard is updated.

8.1.1 Safe editing workflow

  1. Make a copy of the current dashboard.yml before making a substantial change.
  2. Open the file in a plain-text editor and change only the value after the relevant colon.
  3. Keep the existing indentation. YAML uses spaces to show which settings belong together; tabs should not be used.
  4. Save the file, render the Quarto book again, and review the study-wide and relevant site data-quality sections as well as the chart affected by the change.
  5. Record analytically important changes—especially cycle rules, denominators, date cutoffs, and confidence levels—so results from different dashboard versions are not compared as if their definitions were identical.

YAML values have a few conventions:

  • true and false turn options on or off.
  • null means no limit; for example, all pain regions are displayed.
  • Text can be quoted, and dates should remain quoted in YYYY-MM-DD form.
  • Proportions are written between 0 and 1, so 0.80 means 80%.
  • Lists use square brackets, for example [18, 24, 29, 34].

For example, this changes the missed-daily-report alert from three consecutive days to four:

monitoring:
  consecutive_missed_days: 4

8.1.3 Switching between dummy and production data

The controlling setting is:

data_source:
  mode: development

Use development while testing with the dummy datasets. For live Kobo data, enter the correct server and add all deployed asset UIDs to the three lists under data_source.production, store the API token in the environment variable named by api_token_environment_variable, and then change the mode to production.

Each logical input can combine any number of deployed Kobo forms:

data_source:
  production:
    keys_recruitment_forms:
      - "RECRUITMENT_ASSET_SITE_1"
      - "RECRUITMENT_ASSET_SITE_2"
    keys_enrollment_forms:
      - "ENROLLMENT_ASSET_SITE_1"
      - "ENROLLMENT_ASSET_SITE_2"
    keys_daily_forms:
      - "DAILY_ASSET_SITE_1"
      - "DAILY_ASSET_SITE_2"
      - "DAILY_ASSET_SITE_3"

All listed versions must use the same analysis field names. The preparation step downloads each asset, records its source UID in _dashboard_source_asset_uid, combines the rows, and only then runs the normal schema and linkage checks. Duplicate UIDs within a list are ignored to prevent accidental double counting.

The API token itself must not be written into dashboard.yml or committed to GitHub. Production action lists are also excluded from the rendered site by default because they can contain participant identifiers or contact information.

During early live testing, Kobo may omit a question from its JSON response when every downloaded submission skipped that question. The importer therefore treats unanswered monthly outcome fields as empty rather than assuming the connected asset is wrong. When a test record lacks the form’s calculated report date, it uses the calendar day before the Kobo submission timestamp because CIMC questions describe “yesterday.” If no monthly records are yet due, the monthly page displays a “not yet available” explanation and will populate after the first eligible monthly submission. Participant identifiers and the core CIMC routing fields are still validated so an incorrect asset UID or incompatible form does not pass silently.

8.1.4 Settings that change the meaning of results

Some settings affect presentation only, while others change the underlying calculation. Changes to the following should be agreed and documented before results are compared over time:

  • study.data_cutoff, follow-up duration, and monthly due-day rules;
  • participant ID, report-date, programme-start, or pain-location field mappings;
  • any setting under cycle_inference;
  • monitoring thresholds used to construct operational lists;
  • demographic boundaries or site definitions;
  • the confidence level and participant-bootstrap settings.

By contrast, chart titles, the number of intersections displayed, and the visible chart window generally change presentation rather than the source records. A shorter display window can still hide later observations from view, so it should be described clearly.

8.1.5 Rebuilding the dashboard

After saving the configuration, render the complete Quarto project from the project folder. The pre-render step prepares either the dummy or Kobo data, the R code recalculates every page, and the completed HTML book is written to docs/.

quarto render

Do not manually edit files inside docs/: they are generated outputs and will be replaced during the next render. If a render stops after a configuration change, first check spelling, indentation, quote pairing, and whether list labels and boundaries contain compatible numbers of entries.

8.1.6 What the dashboard is written in

All data preparation, statistical summaries, confidence intervals, tables, and plots are implemented in R. The report pages are Quarto documents (.qmd), while dashboard.yml supplies YAML settings. The published HTML also uses CSS for appearance and a small amount of JavaScript for interactive elements such as body-map hover labels. No Python analysis pipeline is used.

8.2 Technical appendix: detailed ever-reported pain location map

This version retains every original SVG region, including left/right and dorsal/ventral distinctions. Locations come only from pain-positive daily submissions; percentages use all unique participants as the denominator, and each participant contributes at most once per detailed region across the observation period.

What it answers. “Did this participant ever report pain in this exact anatomical region during follow-up?” Repeated reports in the same region do not increase that participant’s contribution.

Why it is in the appendix. The detailed map preserves laterality and body surface for clinical or instrument-development review, while the symmetric map earlier in the report provides the clearer primary summary.
